# Store vector archives as file-level S3 objects

Each Archived Vector Index is stored as one versioned, gzip-compressed JSONL object under a deterministic `vector-archive/v1/{file_id}.jsonl.gz` S3 key, while `file_vector_index_state` remains the authoritative lifecycle state. The object is generated through bounded-memory temporary-disk streaming, preserves the vector values returned by the active store without deliberate precision conversion, and is exempt from automatic S3 expiration. Archived chunk and vector content is not stored in MySQL, and the new design carries no MySQL archive fallback because the previous archive implementation was never formally launched. The change deliberately replaces only the storage medium: existing archive and restoration state transitions, retry semantics, batching, and externally visible behavior remain unchanged unless S3 access itself requires an equivalent operation. No upload HEAD/checksum validation, stored source-index version comparison, or additional record for missing online vectors is introduced. A successfully restored object is deleted from S3. This trades relational querying of individual archived chunks for substantially lower write amplification and a storage model aligned with file-level archive and restoration operations; the obsolete tables are removed through a separate operational DDL after the new implementation is stable.

The object records the file ID, schema version, and chunk count needed to retain the existing restoration count check. Archive retry treats an existing object as equivalent to existing MySQL archive detail: if active vectors are already absent, the task may converge the file state to `ARCHIVED`. Restoration continues to write batches of 500 nodes, retains partially restored active vectors on failure, keeps the file state `ARCHIVED`, and retries from the beginning with idempotent vector upserts. After complete restoration and count verification, state changes to `AVAILABLE` before the S3 object is deleted; cleanup failure is warning-only and creates no additional database or Redis record. Complete reindexing and permanent file deletion also make a best-effort attempt to delete the deterministic object. Archive reads and restoration writes remain at 500 nodes per batch.

The archive object contains the same restoration data as the retired MySQL detail rows: node ID, embedding, node type, relationships, document name, and extra metadata. S3 configuration or object access failure fails the operation without a fallback. Existing keys are overwritten by complete newly generated objects; object-store operations raise errors except for boolean existence checks. Object generation uses temporary files so the header can contain the final chunk count without loading all nodes into memory. Existing HTTP endpoints, scheduled tasks, dry-run behavior, progress reporting, task locks, and file locks remain unchanged. All MySQL archive models, mappers, runtime branches, benchmark tooling, and tests are removed, while physical table removal remains a separate manual operation after deployment readiness is confirmed.

File state, not object existence, determines restoration eligibility: only `ARCHIVED` files may restore from S3. Residual objects under `AVAILABLE` or other states are never restored, are best-effort deleted after complete indexing, and may be overwritten by a later archive. Embeddings are stored directly as JSON arrays and the whole JSONL object is gzip-compressed once, without per-vector Base64 encoding. Restoration downloads to temporary storage, streams records in batches, and preserves the current behavior for malformed records and partial vector writes. Objects use `application/x-ndjson` with gzip content encoding. The archive root prefix is configurable per environment, while the `v1` format segment is controlled by code. The existing generic S3 initialization logging is explicitly outside this change.

The implementation uses gzip level 1, keeps archive and restore batches at 500 nodes, and processes files serially. Temporary storage defaults to the system temporary directory and may be redirected through `VECTOR_ARCHIVE_TEMP_DIR`; the task requires at least 1 GiB free before starting and removes strictly named archive temporary files older than 24 hours. S3 operations rely on the SDK retry policy, distinguish a real missing object from transport or permission failure, upload directly to the deterministic final key, and add no business-level total timeout. These choices keep the first S3 release operationally conservative and leave concurrency tuning as a separate measured change.
