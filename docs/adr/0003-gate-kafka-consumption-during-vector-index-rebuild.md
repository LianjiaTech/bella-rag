# Gate kafka consumption of chunk-vector mutations during a vector index rebuild

A store-level Vector Index Rebuild rejects vector writes and deletes on the collection while its index is being rebuilt. Chunk vectors reach the Main Chunk Vector Index only by consuming kafka messages: `KnowledgeIndexTaskListener` writes through file indexing, and `KnowledgeFileDeleteListener` deletes; every other listener mutates QA, summary, or text2qa collections that the rebuild does not touch. If these two listeners stay active during a rebuild, an indexing message is consumed, its write fails against the rebuilding collection, and after the retry limit the message is committed with no vector ever written — the file's content is silently lost. The rebuild therefore requires an operator-controlled Ingestion Suspension of exactly those two listeners, validated at the rebuild submission point before the collection rebuild is submitted.

A single shared switch `KAFKA.VECTOR_INDEX_CONSUME_ENABLED` (environment override `KAFKA_VECTOR_INDEX_CONSUME_ENABLED`, default `true` = consume, preserving current behavior) gates the two chunk-collection listeners. `BaseListener` gains a class-level `consume_switch_key` that a listener sets to declare itself gated; when the switch is off, the gated listeners are not created at startup, reusing the existing "unavailable listener is skipped" path in `get_instance`. The switch is read once at process startup, so toggling it requires a restart. A startup-read switch was chosen over a runtime toggle because the environment is read at boot, the fail-closed property holds (a process whose environment was changed but not restarted still validates against the old value and refuses the rebuild), and the operation is a rare deliberate maintenance window where a restart is acceptable. A single shared switch was chosen over per-listener switches because both listeners must stop together and one switch keeps the rebuild validation a single check.

The rebuild submission point validates two preconditions before submitting, returning `409 Conflict` on failure: (1) the switch must be off; (2) the collection's `indexStatus` must not indicate an in-progress build, guarding against duplicate rebuild submissions. The submission succeeds only when both hold.

Consumption resumes from the last committed offset: `KafkaConsumer` keeps `auto.offset.reset=earliest` and `enable.auto.commit=False` with manual commit on success, and a unit test asserts this so the guarantee cannot regress. While the gated listeners are absent, the consumer group's committed offsets persist, so re-enabling after the rebuild replays every message that arrived during the suspension rather than skipping it. One caveat: if a rebuild outlasts the kafka offset-retention window (default about seven days) with no group member, offsets expire and the group restarts from earliest — a duplicate replay, not a loss, mitigated by the existing redis-based indexing dedup.

Out of scope, documented rather than enforced: HTTP-triggered indexing that bypasses kafka is not gated, so the operating procedure must drain in-flight indexing and avoid such indexing during the window; per-file re-indexing is independent of the kafka-consumption concern and is not gated.

This trades a restart-requiring operational interlock for the guarantee that no file content consumed during a rebuild is lost. Alternatives considered and rejected: a runtime config toggle (rejected: contradicts the environment-variable mechanism and adds a dynamic-config dependency for a rare operation), per-listener switches (rejected: both listeners must stop together, and one switch keeps validation single-check), gating inside the consume loop (rejected: pointless for a static switch), and merely warning on rebuild (rejected: does not prevent the loss).
